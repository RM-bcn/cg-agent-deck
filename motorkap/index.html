1

Er komt iets binnen

GitHub stuurt een webhook: een HTTP-verzoek met een JSON-body op het moment dat een workflow klaar is. Geen e-mail, geen polling. De body is precies dit:

POST /hooks/github
X-GitHub-Event: workflow_run
X-Hub-Signature-256: sha256=9f2c…

{
  "action": "completed",
  "repository": { "full_name": "RM-bcn/Naxos-bus-pwa" },
  "workflow_run": {
    "id": 40682011246,
    "name": "Refresh transit data",
    "conclusion": "failure",
    "head_branch": "main",
    "html_url": "https://github.com/.../runs/40682011246"
  }
}

Dezelfde poort ontvangt ook POST /hooks/vercel?token=… en POST /ingest/email voor een doorgestuurde mail. Drie deuren, één inlaat.

2

De deur gaat alleen open met de juiste handtekening

Iedereen kan een POST naar je poort sturen. Daarom controleert de server een HMAC-SHA256: GitHub en jij delen een geheim, en alleen een body die met dat geheim is ondertekend komt door. Zonder match: 401, geen verwerking.

// src/ingest.mjs
const expected = 'sha256=' + crypto
  .createHmac('sha256', GH_SECRET)
  .update(rawBody)
  .digest('hex');

timingSafeEqual(header, expected)  // anders 401
3

De melding wordt een feit met een naam

De payload wordt vertaald naar één event. De belangrijkste regel is de fingerprint: dezelfde oorzaak krijgt altijd dezelfde string. Daardoor worden twintig mislukte runs één incident in plaats van twintig berichten.

{
  "source":      "github",
  "kind":        "workflow_failed",
  "fingerprint": "gh:RM-bcn/Naxos-bus-pwa:data:main",
  "severity":    "p0",
  "title":       "Datapijplijn gefaald (main)",
  "url":         "https://github.com/.../runs/40682011246"
}

De severity komt uit de regel, niet uit het gevoel: data of productie → p0, preview of overige workflow → p1, mail → p1/p2.

4

Dedupe: twintig runs, één incident

De inlaat zoekt een open incident met dezelfde fingerprint. Gevonden? Dan telt hij op en werkt hij de laatste melding bij. Niet gevonden? Dan maakt hij er één aan.

// src/incident.mjs
const existing = openFor(incidents, fingerprint);
if (existing) {
  existing.count += 1;        // 20 runs → count: 20
  existing.lastSeen = now;
} else {
  createIncident({ ... });    // eerste keer
}

Dit is het bestand dat daaruit komt. Eén incident, met een teller en een status:

{
  "id":          "inc_d63ace06281d",
  "fingerprint": "gh:RM-bcn/Naxos-bus-pwa:data:main",
  "severity":    "p0",
  "title":       "Datapijplijn gefaald (main)",
  "count":       20,
  "status":      "open",
  "firstSeen":   "2026-10-28T20:39:41Z",
  "notifications": 1
}

Een groene run met dezelfde fingerprint zet status: "resolved". Dat is de fout die de oude watchdog maakte: issues gingen open en nooit meer dicht.

5

Vier bestanden, elk met één taak

events.ndjson
alles wat binnenkwam, append-only. Het ruwe spoor.
incidents.json
de teller en de status. Hier gebeurt de dedupe.
state.json
afgeleide samenvatting. De cockpit en de agent lezen alleen dit.
outbox.ndjson
elk bericht dat (niet) verzonden is. Je bewijs dat er iets uit ging.

state.json is bewust dom: geen logica, alleen de stand van zaken. Daardoor kan dezelfde data naar de pagina, naar Telegram en naar de agent.

{
  "generatedAt": "2026-10-28T20:40:40Z",
  "counts": { "open": 5, "p0": 4, "resolved24h": 1 },
  "lanes": {
    "trust": [ { "title": "Deploy gefaald: paros (production)", ... } ],
    "data":  [ { "title": "Datapijplijn gefaald (main)", ... } ]
  },
  "inbox": [ "Datapijplijn", "paros", "ios" ]
}
6

En dan pas een bericht

Melden is een poort, geen automatisme. p0 gaat direct. p1 en p2 worden gebundeld, met een maximum van drie per dag. Elk incident onthoudt wanneer het voor het laatst meldde, zodat je niet elke 15 minuten hetzelfde hoort.

// outbox.ndjson — echt verzonden of niet
{ "severity": "p1", "sent": false,
  "text": "🟡 P1 · CI gefaald (main)
RM-bcn/CycladesGo-portal · conclusie failure · run 999001
https://github.com/.../runs/999001" }

In productie staat hier "sent": true en gaat het naar je telefoon. Nu, zonder bot-token, blijft het in de outbox staan — zichtbaar, niet verzonden.

7

De agent: pas wakker als er werk is

Elke 15 minuten draait er een klein script. Het kijkt naar state.json en doet niets als er geen open p0/p1 is. Is er wel werk, dan start het één run met een lock, een tijdslimiet en een tokenbudget.

# src/run-if-needed.mjs
lock exists?        → stop
no open p0/p1?      → stop
otherwise:
  opencode run --auto --model opencode-go/deepseek-v4.1-flash \
    "Lees data/state.json. Pak het oudste open p0/p1.
     Onderzoek de oorzaak met bewijs (joblog, commit, bestand:regel).
     Data of parser: branch agent/<id>, fix, gate, PR. Nooit main.
     Bron of tarief: stel een vraag, wijzig niets.
     Schrijf een incidentverslag en stop."

De agent werkt in een eigen checkout, op een eigen branch. Hij schrijft geen data en pusht niet naar main. Het resultaat is een PR plus een verslag; jij merget.

Eerlijk: dit is de enige stap die nog niet gebouwd is. Stap 1–6 draaien en zijn getest; stap 7 is het script dat de agent aanroept.
